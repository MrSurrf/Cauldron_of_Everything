# Контракт API пространства «Мой стол»

Статус: **предложение для бэкенд-разработчика, не реализованный сервер**.
В этой итерации изменяется только frontend. Действующий API энциклопедии и
проверка сессии остаются прежними. Закрытые схемы сохраняются в localStorage;
никаких запросов публикации или записи закрытого документа фронтенд не делает.

## Действующие запросы

- `GET /api/auth/session/` — существующий вход в приложение.
- `GET /api/encyclopedia/?type=creature&q=...&page=1&page_size=30` — библиотека.
- `GET /api/encyclopedia/{id}/` — исходная Entity, только чтение.

Типы библиотеки: `creature`, `class`, `race`, `background`, `feat`, `spell`,
`item`, `reference`. `reference` предлагается для справочных материалов:
в текущей БД этого типа и содержимого правил ещё нет; UI показывает пустое
состояние, а не выдуманные записи. Существующий `sidekick` поддерживается
форматом ссылок. Размещение никогда не вызывает DELETE/PATCH Entity.

## Предлагаемые запросы, к которым подготовлен frontend

Все запросы используют существующий `authFetch` с Bearer JWT.
Для новых ресурсных API передаётся `forbiddenScope: resource`: `403` оставляет
сессию сайта активной, но не открывает ресурс. `401` по-прежнему обновляет JWT
или завершает сессию. Проверка `/auth/session/` сохраняет прежнюю строгость.

| Метод и путь | Ответ / доступ |
| --- | --- |
| `GET /api/characters/?q=&page=1&page_size=30` | Только персонажи/NPC, доступные текущему пользователю |
| `GET /api/characters/{id}/` | Материал после объектной проверки доступа |
| `GET /api/campaigns/?q=&page=1&page_size=30` | Только кампании владельца/участника |
| `GET /api/campaigns/{id}/` | Только разрешённые поля кампании |
| `GET /api/campaigns/{id}/table/public/` | Только отдельная публичная проекция после проверки участия |

Списки: `{ "count": 1, "results": [material] }`; страницы нумеруются с 1.
Поиск и пагинация выполняются **после** фильтрации queryset по доступу.
`count` не должен раскрывать количество чужих материалов.

`material`:

```json
{
  "id": "uuid-or-string-id",
  "entityType": "character",
  "name": "Имя персонажа",
  "slug": "character-slug",
  "facts": ["Воин", "Уровень 3"],
  "description": "Описание в формате существующего ContentEditor"
}
```

`entityType` — `character` / `npc` для characters, `campaign` для campaigns.
Карточка запрашивает тот же объект по ID; никаких изменений оригинала.
`401/403` — нет доступа, `404` — недоступный объект/ещё не подключённый источник,
`501` — источник пока не реализован. UI сообщает об ошибке без локального fallback.

## Публичный документ

```json
{
  "visibility": "public",
  "revision": 1,
  "document": {
    "version": 3,
    "activeId": "diagram-public",
    "entities": [{ "id": "location-public", "slug": "location-public", "entityType": "location", "name": "Таверна", "description": "Общее описание", "facts": "", "state": "" }],
    "layout": { "libraryWidth": 336, "inspectorWidth": 380, "section": "creature", "query": "" },
    "diagrams": [{
      "id": "diagram-public",
      "name": "Доступная игрокам схема",
      "viewport": { "x": 0, "y": 0, "zoom": 1 },
      "nodes": [{
        "id": "instance-public",
        "type": "location",
        "position": { "x": 100, "y": 100 },
        "width": 240,
        "data": { "entityId": "location-public" }
      }],
      "edges": []
    }]
  }
}
```

Публичная проекция должна содержать только разрешённые сервером Entity и их
размещения; закрытые описания и записи нельзя включать в `entities`.
Frontend требует `visibility: public`, валидирует формат документа и открывает
его только для чтения. Он **не читает localStorage закрытого стола**, не открывает
библиотеку, не загружает исходные Entity/персонажей по ссылкам из публичного
документа и не записывает этот ответ в localStorage. Ошибка доступа/сети/формата
оставляет публичный экран пустым. Переключение кампании размонтирует прошлый экран.
`/my-table?table=public&campaign={id}` — прямая ссылка.

Сервер обязан до сериализации:

1. Проверить JWT, активность пользователя, членство в кампании и разрешение
   чтения публичного стола. Участник не получает закрытый документ даже зная ID.
2. Выбирать отдельную опубликованную проекцию, а не полный документ с флагами
   `hidden`. Удалить приватные схемы, Entity из `document.entities[]`, узлы,
   вложенные объекты, связи и подписи к ним.
3. Не переносить приватные заметки, состояние, HTML/контент, имена или ID
   источников, search query и другие приватные поля в публичный ответ.
   `description`, `state`, `facts` публичного узла — только явно опубликованные значения.
4. Проверить ссылки контейнеров и рёбра после фильтрации. Нельзя оставлять ID
   скрытых объектов в `entityId`, `locationId`, `source`, `target` или `reference`.
5. Отдавать `Cache-Control: private, no-store`; не помещать приватные документы
   в общедоступный кэш, логи или ответы об ошибках. Повторять проверки на каждом запросе.

Frontend не может заменить серверную авторизацию. Текущий закрытый режим —
**локальный черновик профиля браузера, не защищённое серверное хранилище**.
Он доступен тому, у кого есть доступ к этому браузерному профилю. Не утверждать,
что требования серверных прав реализованы до появления и проверки API.

## Формат документа v3 и последующая серверная запись

Точный TypeScript-контракт и валидатор: `model/table.ts`. Все содержательные данные
находятся в `document.entities[]`: `{ id, entityType, slug, name, description, facts,
state, reference? }`. Поддерживаются `playerCharacter`, `npc`, `creature`, `location`,
`quest`, `faction`, `item`, `spell`, `note` и прежние разделы библиотеки.
Входной API-тип `character` преобразуется в `playerCharacter`; NPC остаётся отдельным типом.

- Каждый узел содержит только собственный UUID, `type: entity|location|note`,
  `position`, необязательные `width`/`height`, `data: { entityId, locationId? }`.
  `data.entityId` ссылается на Entity уровня стола. Размеры отсутствуют для авторазмера.
  Содержательные поля в `node.data` отклоняются валидатором.
- `reference` принадлежит Entity: `{ source: encyclopedia|character|campaign,
  entityId, entityType, name, slug, facts: string[] }`. Оригинал не изменяется.
  Новый DnD из библиотеки создаёт независимую Entity-экземпляр со ссылкой на оригинал.
  Размещение на другой схеме использует ту же Entity; правки отражаются во всех её размещениях.
- `data.locationId` — существующая группировка размещений в той же схеме, только для creature/playerCharacter/npc.
  Дети хранятся плоско, визуально показаны списком. Вложенные локации запрещены.
- Ребро: `{ id, source, target, label?,
  data?: { description?: string } }`. Нет связей между схемами или с отсутствующими узлами.
- `description` использует формат существующего ContentEditor, не сырой доверенный HTML.
- Удаление контейнера извлекает детей на холст; удаление экземпляра удаляет его
  рёбра, но никогда не Entity. Дублирование контейнера создаёт пустой контейнер.

Формат v1/v2 читается через изолированный legacy-валидатор и миграцию. ID узлов,
координаты, изменённые размеры, подписи и локальные правки сохраняются. Ключ
localStorage не меняется: `cauldron.campaign-table.v2`. Новая запись имеет `version: 3`.
Точки контура и технические якоря React Flow вычисляются только в UI, в документ не входят.

Предлагаемые **будущие**, пока не вызываемые frontend запросы:

- `GET /api/campaigns/{id}/table/private/` → `{ visibility: private, revision, document }`;
- `PUT /api/campaigns/{id}/table/private/` с `If-Match: revision` → новая revision;
- отдельный явный endpoint публикации выбранной проекции (не синхронизация private → public).

Владелец/уполномоченный редактор может читать и записывать private, игрок — нет.
PUT обязан атомарно валидировать схему, размеры/координаты/лимиты, права на все
references и принадлежность узлов кампании. Конфликт revision → `409/412`, без
перезаписи нового документа. Импорт localStorage в кампанию — отдельное явное
действие после выбора владельца/кампании, не автоматическая загрузка приватных заметок.

Обязательные серверные тесты: анонимный отказ; чужой ID; игрок → private GET/PUT;
приватный потомок публичной локации; ребро к скрытому узлу; приватные поля публичного
узла; недоступная Entity; отзыв участия; пагинация/count; конфликт revision.
Эти проверки не имитируются фронтенд-тестами как якобы реализованная серверная защита.
